## 1. О проекте

**Исходное задание.** Разработать на React интерфейс для отправки и получения сообщений в MAX через GREEN-API. Отправка — методом [SendMessage](https://green-api.com/v3/docs/api/sending/SendMessage/), получение — по технологии [HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/) (методы ReceiveNotification и DeleteNotification). Интерфейс — в стиле привычного мессенджера.

**Реализованный сценарий:**

1. Пользователь открывает сайт и вводит учётные данные GREEN-API: `apiUrl`, `idInstance`, `apiTokenInstance`.
2. Вводит номер телефона получателя и создаёт новый чат.
3. Пишет текстовое сообщение и отправляет его получателю в MAX.
4. Получатель отвечает в MAX на телефоне.
5. Пользователь видит ответ в чате на сайте.

Дополнительно есть **демо-режим** (кнопка на экране входа). Он работает без GREEN-API на мок-реализации, чтобы интерфейс можно было посмотреть без аккаунта.

Что ещё есть в интерфейсе: статусы сообщений (часы / ✓ / ✓✓ / синие ✓✓ / ошибка), автоматическое создание чата при сообщении от нового собеседника, подстановка имени контакта вместо номера, разделители по дням, счётчик непрочитанных, адаптивная вёрстка, светлая и тёмная темы.

**Стек:** Vite, React 19, TypeScript (strict, `noUncheckedIndexedAccess`), zustand, zod, vitest + jsdom. UI-библиотек нет: свои компоненты и обычный CSS с CSS-переменными.

## 3. Подготовка GREEN-API

Подробно — в разделе документации [«Перед началом работы»](https://green-api.com/v3/docs/before-start/).

1. **Установите MAX на телефон** и зарегистрируйтесь по номеру телефона. Для авторизации по QR-коду в MAX сейчас нужно отключить пароль для входа.
2. **Зарегистрируйтесь в [личном кабинете GREEN-API](https://console.green-api.com)**: e-mail, страна, подтверждение кодом из письма.
3. **Создайте инстанс для MAX**: «Создать инстанс» → выберите тариф (для теста подходит бесплатный «Разработчик»). Инстанс переходит в рабочее состояние примерно за 2 минуты.
4. **Привяжите аккаунт MAX**: в кабинете откройте инстанс → «Получить QR-код». На телефоне в MAX: *Профиль → Устройства → Войти по QR-коду* — отсканируйте код. Состояние инстанса должно стать `authorized`.
5. **Скопируйте параметры доступа** из карточки инстанса:
   - `apiUrl` — адрес API, например `https://1103.api.green-api.com`. У каждого инстанса он свой, поэтому вводится вручную, а не зашит в код;
   - `idInstance` — номер инстанса;
   - `apiTokenInstance` — ключ доступа.
6. **Включите уведомления**: в настройках инстанса («Изменить») включите
   - «Получать уведомления о входящих сообщениях и файлах» (`incomingWebhook`);
   - «Получать уведомления о сообщениях, отправленных через API» (`outgoingAPIMessageWebhook`);
   - «Получать уведомления о статусах отправленных сообщений» (`outgoingWebhook`);
   - по желанию: «…о сообщениях, отправленных с телефона» (`outgoingMessageWebhook`). Тогда в чате появятся и сообщения, отправленные с телефона, а по [документации](https://green-api.com/v3/docs/api/receiving/notifications-format/statuses/OutgoingMessageStatus/) эта настройка нужна и для статусов;
   - по желанию: «…об изменении состояния авторизации» (`stateWebhook`).

   **Поле `webhookUrl` должно быть пустым.** Иначе HTTP API не отдаёт уведомления ([ReceiveNotification](https://green-api.com/v3/docs/api/receiving/technology-http-api/ReceiveNotification/) возвращает 400), и приложение покажет об этом сообщение. Текущие настройки можно посмотреть методом [GetSettings](https://green-api.com/v3/docs/api/account/GetSettings/), а изменить в кабинете или методом [SetSettings](https://green-api.com/v3/docs/api/account/SetSettings/). Приложение настройки инстанса **не меняет**, чтобы не трогать чужую конфигурацию без спроса.

## 4. Как проверить сценарий

### С реальным аккаунтом

1. `npm run dev`, откройте http://localhost:5173.
2. Введите `apiUrl`, `idInstance`, `apiTokenInstance` и нажмите «Войти». Приложение проверит инстанс через GetStateInstance. Если аккаунт MAX не привязан или инстанс запускается, вход не откроется и появится понятная ошибка.
3. В поле «Новый чат» слева введите номер собеседника (РФ или РБ) в любом виде: `+7 (999) 123-45-67`, `8 999 123 45 67`, `+375 29 …`. Нажмите «+» или Enter. Приложение найдёт chatId через CheckAccount и откроет чат. Если на номере нет MAX, появится «На этот номер не зарегистрирован MAX».
4. Напишите сообщение и нажмите Enter (Shift+Enter — перенос строки). Пузырь появится сразу с часами. Дальше статус меняется на ✓ (отправлено), ✓✓ (доставлено) и синие ✓✓ (прочитано).
5. Ответьте с телефона получателя. Ответ появится в этом же чате в течение пары секунд, а номер в заголовке сменится на имя контакта.

Дополнительно стоит проверить:
- перезагрузку страницы (F5): сессия восстанавливается без повторного ввода;
- сообщение от нового собеседника: чат создаётся автоматически;
- неверный токен: ошибка на экране входа;
- непустой `webhookUrl`: в сайдбаре появится пояснение и кнопка «Повторить».

### Демо-режим

На экране входа нажмите «Демо-режим без GREEN-API». Сеть не используется:
- через секунду придёт сообщение от «Поддержка (демо)» — так выглядит входящее от нового контакта;
- создайте чат по любому номеру РФ/РБ. Номер, оканчивающийся на `0000`, считается незарегистрированным в MAX;
- отправьте сообщение: статусы меняются как в настоящем API, через ~3 с придёт ответ, и номер в заголовке сменится на имя;
- сообщение со словом «ошибка» получит статус «не отправлено».

### Порты

| Порт | Контракт | Реализации |
|---|---|---|
| `MessengerGateway` | `capabilities` (лимиты), `getConnectionState`, `findContactByPhone`, `sendText`, `subscribe`. Бросает только доменные ошибки. | `GreenApiGateway`, `MockGateway` |
| `NotificationSource` | `start(handlers) → stop`: сырые уведомления, временные проблемы, фатальная ошибка. | `HttpPollingSource` |
| `CredentialsStore` | `load / save / clear` конфигурации сессии, никогда не бросает. | `SessionCredentialsStore` |
| `GatewayFactory` | `(SessionConfig) → MessengerGateway` | функция в `composition.ts` |

Компоненты получают шлюз через `useGateway()` и не импортируют реализации. Имена полей API (`typeWebhook`, `idMessage`, `textMessageData`) встречаются только в `infrastructure/greenapi`. Токен подставляется в URL только внутри `HttpClient`.

### Поток данных: отправка

1. `Composer` → `useSendMessage.send(chatId, text)`.
2. В хранилище добавляется сообщение со временным id `local-…` и статусом **pending** (оптимистично).
3. `gateway.sendText` → `HttpClient` → `POST {apiUrl}/waInstance{id}/sendMessage/{token}` с телом `{ chatId, message }`.
4. Ответ `{ idMessage }`: временный id заменяется настоящим, статус становится **queued** (сообщение в очереди GREEN-API).
5. Ошибка запроса → статус **failed** с текстом причины; `AuthError` дополнительно закрывает сессию.
6. Дальше статусы приходят уведомлениями (см. «Получение»).

### Поток данных: получение

1. `useMessengerSync` подписывается на `gateway.subscribe`. Шлюз запускает `HttpPollingSource` (один на все подписки).
2. Цикл: `GET receiveNotification?receiveTimeout=20` (long polling) → уведомление или пусто.
3. Сырое тело уходит в `mapNotification` → доменное событие (`message` / `status` / `connection`) или `null` для ненужных типов.
4. Событие применяется чистой функцией `applyEvent` (upsert по id, слияние статусов).
5. `DELETE deleteNotification/{receiptId}` — даже если обработка упала. Затем сразу следующий `receiveNotification`.

### Жизненный цикл статуса исходящего сообщения

```
pending ──SendMessage OK──▶ queued ──эхо outgoingAPIMessageReceived──▶ sent ──delivered──▶ delivered ──read──▶ read
   │                          │                                          │
   └──ошибка запроса──────────┴──────── failed / noAccount / notInGroup ─┴──▶ failed (финальный, с причиной)
```

Статус только растёт и никогда не откатывается (уведомления могут прийти не по порядку). `failed` финальный. Поздний `failed` не перечёркивает уже подтверждённые `delivered`/`read`. В интерфейсе: часы (pending, queued) / ✓ (sent) / ✓✓ (delivered) / синие ✓✓ (read) / красный значок с текстом ошибки (failed).

## 6. Используемые методы API

| Метод | HTTP | Зачем | Документация |
|---|---|---|---|
| SendMessage | `POST` | отправка текста (до 4000 символов) | [ссылка](https://green-api.com/v3/docs/api/sending/SendMessage/) |
| ReceiveNotification | `GET` | получение уведомления из очереди (long polling) | [ссылка](https://green-api.com/v3/docs/api/receiving/technology-http-api/ReceiveNotification/) |
| DeleteNotification | `DELETE` | подтверждение обработки уведомления | [ссылка](https://green-api.com/v3/docs/api/receiving/technology-http-api/DeleteNotification/) |
| GetStateInstance | `GET` | проверка учётных данных и состояния аккаунта при входе | [ссылка](https://green-api.com/v3/docs/api/account/GetStateInstance/) |
| CheckAccount | `POST` | номер телефона → chatId пользователя MAX | [ссылка](https://green-api.com/v3/docs/api/service/CheckAccount/) |

**Почему, кроме обязательных методов, нужны GetStateInstance и CheckAccount:**

- **GetStateInstance.** Без него неверный токен, отвязанный от инстанса аккаунт MAX или запускающийся инстанс проявились бы только при первой отправке, в виде непонятной ошибки. Проверка при входе сразу показывает понятную причину (`notAuthorized` — «отсканируйте QR-код», `starting` — «подождите» и т.д.).
- **CheckAccount.** В MAX chatId личного чата — числовая строка (`"10000000"`), а не номер телефона. Отправить можно и по `79991234567@c.us`, но [документация](https://green-api.com/v3/docs/api/chat-id/) прямо предупреждает: ответы и статусы тогда придут с chatId, назначенным сервером, и не сопоставятся с чатом. То есть шаг 5 сценария («видит ответ в чате») не работал бы надёжно. Поэтому чат создаётся с chatId из CheckAccount, а заодно сразу видно, есть ли на номере MAX.

## 7. Принятые решения и компромиссы

- **Long polling без `setInterval`.** ReceiveNotification сам держит запрос до 20 с, пока не появится уведомление. Последовательный цикл «получить → обработать → удалить → снова получить» даёт минимальную задержку и не создаёт параллельных запросов к одной FIFO-очереди (иначе одно уведомление получили бы дважды или нарушили порядок). При сетевых ошибках — экспоненциальная пауза 1 → 2 → 4 … 30 с.
- **CheckAccount перед созданием чата.** См. раздел 6. CheckAccount вызывается только по явному действию пользователя, а не на ввод. Номера, у которых нет MAX, запоминаются и повторно не проверяются: MAX ограничивает частые проверки.
- **zustand + чистые функции.** Вся логика (upsert, гонки эха и статусов, сортировка) — в `chatState.ts`: функции «состояние → новое состояние» без React и сети, которые легко покрыть unit-тестами. zustand — тонкая обёртка с минимальным API и точечными подписками без Provider-обвязки. Хранилище создаётся на каждую сессию, поэтому выход из аккаунта гарантированно очищает переписку.
- **sessionStorage для учётных данных.** Переживает F5, но не закрытие вкладки. Токен даёт полный доступ к аккаунту, и хранить его бессрочно в localStorage рискованно. Доступ к storage обёрнут в try/catch (приватный режим, запрет cookies), данные проверяются схемой при чтении.
- **zod на границе системы.** Ответы и уведомления проверяются там, где приходят из сети. Битое или незнакомое уведомление не роняет приложение: маппер возвращает `null`, и уведомление просто подтверждается. Схемы описывают только используемые поля, поэтому новые поля в API ничего не ломают.
- **Без UI-библиотек.** Интерфейс небольшой: несколько примитивов и ~18 КБ CSS. Библиотека добавила бы вес и чужой визуальный язык. Все цвета — CSS-переменные, тёмная тема через `prefers-color-scheme`.
- **Визуальный язык веб-версии MAX.** Раскладка (навигационная колонка 77px, список чатов 393px, окно чата), палитра темы «space» для светлой и тёмной схем, радиусы пузырей (16px, 6px внутри «стопки»), типографика и плавающая панель ввода сверены с CSS-переменными web.max.ru. Фирменная графика MAX (логотип, узор обоев) не копировалась: узор фона нарисован свой.
- **Доменные имена вместо имён API.** `Message.id`/`content.text` вместо `idMessage`/`textMessage`, `ConnectionState: 'ready' | 'restricted' …` вместо `authorized | suspended`. Смена провайдера не затрагивает фичи и UI.
- **Branded `ChatId`.** Тип не даёт случайно передать номер телефона туда, где нужен chatId (самая вероятная ошибка в этой задаче).
- **Демо-режим как отдельная реализация шлюза**, а не флаги в компонентах. Мок воспроизводит эхо, статусы, ответы и ошибки, поэтому в демо работают те же ветки кода, что и с настоящим API.
- **История не загружается.** Задание описывает живую переписку, а GetChatHistory имеет лимит 1 запрос в секунду. Как добавить историю — см. раздел 9.
- **Статус `suspended`** (временные ограничения аккаунта) не мешает входу: отправка контактам работает, а в сайдбаре висит предупреждение.

## 8. Обработка ошибок и краевых случаев

| Ситуация | Поведение |
|---|---|
| Повторная доставка уведомления (DeleteNotification не прошёл) | upsert по id — дубля нет |
| Эхо `outgoingAPIMessageReceived` нашего сообщения | upsert по id, статус повышается до `sent` |
| Эхо пришло **раньше** ответа SendMessage | при подтверждении временное сообщение удаляется, а не дублируется |
| Статус пришёл **раньше**, чем стал известен idMessage | хранится в `orphanStatuses` и применяется, когда появится сообщение |
| Статусы пришли не по порядку | статус только растёт, `failed` финален |
| Ответ на сообщение в чате, созданном по номеру | приходит с тем же chatId (из CheckAccount), имя из `chatName` заменяет номер |
| Входящее от нового собеседника | чат создаётся автоматически, растёт счётчик непрочитанных |
| Неподдерживаемый тип (фото, стикер…) | заглушка «Стикер — этот тип сообщений пока не поддерживается» |
| Неизвестный тип уведомления или битые данные | игнорируется и удаляется из очереди |
| Ошибка в обработчике уведомления | уведомление всё равно удаляется, очередь не блокируется |
| Сетевая ошибка / 5xx / 429 при опросе | повтор с паузой 1 → 30 с, предупреждение «Переподключаемся…» |
| Выход, размонтирование, StrictMode | AbortController обрывает и висящий long poll; один источник на все подписки — двух циклов не бывает |
| 401, 403, истёкший или удалённый инстанс | `AuthError` → выход с причиной на экране входа |
| 403 «Your account is suspended» | `AccountRestrictedError` — ограничения аккаунта, отправка только контактам |
| 429 / 466 / 469 | `RateLimitError` (для CheckAccount — с рекомендацией подождать) |
| 400 «custom webhook url is set» | `ConfigurationError`: цикл останавливается, в сайдбаре объяснение и кнопка «Повторить» |
| 400 «instance is starting or not authorized» | `InstanceNotReadyError`, временная ошибка с повтором |
| Прочие 400 | `ValidationError` |
| Обрыв сети, CORS, таймаут | `NetworkError` |
| CheckAccount вернул 200 с `{ status: false, reason }` | разбирается отдельно: лимит / инстанс не готов / прочее |
| Вход при `notAuthorized` / `starting` / `blocked` | понятный текст ошибки, сессия не открывается |
| Номер в любом формате | `+7 (999) 123-45-67`, `8 999…`, `999…`, `+375…`, `80 29…` нормализуются. Не РФ/РБ — ошибка до запроса |
| На номере нет MAX | «На этот номер не зарегистрирован MAX», повторно номер не проверяется |
| Текст длиннее 4000 символов | счётчик с 90% лимита, кнопка отправки блокируется. Лимит берётся из `gateway.capabilities` |
| Недоступный sessionStorage | приложение работает, просто без восстановления сессии |

## 9. Как расширять

**Новый метод API (например, отправка файла или история чата).**
1. В `domain/models.ts` — новый вариант `MessageContent` (например, `{ kind: 'file'; url; name }`).
2. В `domain/ports.ts` — метод порта: `sendFile(...)` или `loadHistory(chatId, before?)`.
3. В `infrastructure/greenapi/schemas.ts` — схема ответа, в `GreenApiGateway` — реализация через `this.http.request({ apiMethod: 'sendFileByUrl', … })`. Для GetChatHistory — маппинг элементов истории в `Message` в `mappers.ts`.
4. В `chatState.ts` — чистая функция, например `prependHistory`, которая сливает сообщения через тот же upsert.
5. В UI — хук и компонент. Существующий код не меняется, TypeScript сам покажет, где нужно обработать новый `kind`.

**Другой мессенджер (WhatsApp, Telegram через GREEN-API или совсем другой провайдер).** Новая реализация `MessengerGateway` (со своими схемами и мапперами) и одна строка в `app/composition.ts`. Формат URL у GREEN-API одинаков для всех мессенджеров, поэтому `HttpClient` и `HttpPollingSource` переиспользуются как есть.

**Вебхуки через свой бэкенд.** Бэкенд принимает вебхуки GREEN-API и отдаёт их браузеру по SSE или WebSocket. На фронтенде — новая реализация `NotificationSource` (например, `SseSource`), которая передаётся в `GreenApiGateway` вместо `HttpPollingSource`. Мапперы и всё выше не меняются.

**Токен на сервере.** Бэкенд-прокси хранит `apiTokenInstance` и добавляет его к запросам. Меняется только `HttpClient`: он строит URL вида `/api/greenapi/{method}` и отправляет cookie сессии. Экран входа и `Credentials` упрощаются до логина в своём бэкенде.

**Своя аутентификация.** Новая реализация `CredentialsStore` (или сервис сессии) и логика `login` в `SessionProvider`. Фичи чата зависят только от `useGateway()` и не заметят разницы.

**Смена темы или UI.** Цвета, радиусы и тени — переменные в `:root` в `app/styles.css`. Компоненты в `ui/` «глупые» и не знают о чатах. Компоненты фич получают данные из хуков, поэтому их можно переписать на любую библиотеку, не трогая модель и инфраструктуру.

## 10. Ограничения и безопасность

- **Токен в браузере.** `apiTokenInstance` хранится в sessionStorage и виден в DevTools и в URL запросов (так устроен формат GREEN-API). Для тестового задания это допустимо. В продакшене нужен бэкенд-прокси, который хранит токен на сервере (см. раздел 9).
- **Несколько вкладок делят одну очередь уведомлений.** Каждое уведомление получит только одна из вкладок. Решение — BroadcastChannel: одна вкладка-лидер опрашивает очередь и рассылает события остальным. Встраивается как ещё одна реализация `NotificationSource`.
- **CORS.** Приложение обращается к GREEN-API напрямую из браузера. Если провайдер или корпоративная сеть заблокирует кросс-доменные запросы, браузер сообщит об этом как о сетевой ошибке («Нет связи с сервером»), отличить её от обрыва сети нельзя. Решение — тот же бэкенд-прокси или прокси dev-сервера Vite.
- **История не сохраняется.** После перезагрузки переписка пустая: показываются только сообщения, пришедшие в текущей сессии. Неподтверждённые уведомления (за последние 24 часа) при этом не теряются — их отдаст очередь.
- **Номера только РФ и РБ.** CheckAccount принимает только коды 7 и 375.
- **Поддерживается только текст.** Остальные типы показываются заглушкой.
